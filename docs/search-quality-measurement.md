# 검색 품질 측정

측정: **2026-10-07, `590f049b95b0bf82e238890970066d84eb75967d`**. 기존 DB 검색(LIKE)을 기준선으로 두고, LIKE로는 찾지 못하는 검색어에서 Lucene이 원래 이슈를 찾는지와 첫 페이지 응답 시간을 잰다.

이 문서의 **식별자(identifier)는 코드 이름**을 뜻한다. 예: `SocketTimeoutException`, `user_id`, `com.example.Foo`. `[Bug]` 같은 제목 머리말 분류와는 별개다. "기존 표본"은 최초 검색어 표본 1,731개, "추가 식별자 표본"은 코드 이름 부분 검색을 추가로 표집한 1,640개다. `identifierPart` 8건은 기존 표본에 포함된 코드 이름 부분 검색이다.

## 방법

**정답 이슈 찾기(known-item).** 이슈를 무작위로 300개 뽑고(seed 843), 각 이슈의 제목·본문·댓글 문장을 아래 규칙으로 바꿔 검색어를 만든다. 원래 이슈가 결과에 있는지, 몇 번째인지를 잰다. 사람이 관련도를 판정하지 않으며 원문을 공개하지 않고도 재현할 수 있다.

| 유형 | 규칙 | LIKE |
|---|---|---|
| `exact` | 연속된 한글 두 단어 그대로 (대조군) | 찾음 |
| `separated` | 같은 문장에서 3–7단어 떨어진 두 단어 | 못 찾음 |
| `reordered` | 연속된 두 단어의 순서를 바꿈 | 못 찾음 |
| `inflected` | `배포했습니다` → `배포된`, `복구됩니다` → `복구하는` | 못 찾음 |
| `particle` | 조사 교체 `오류가` → `오류를`. 어간이 같은 이슈에 다른 형태로도 있을 때만 | 못 찾음 |
| `joined` | 조사·어미 없는 두 단어를 붙임 `권한 설정` → `권한설정` | 못 찾음 |
| `identifierSplit` | `user_id`, `com.example.Foo`의 구분자를 공백으로 | 못 찾음 |
| `identifierPart` | `NullPointerException` → `PointerException` | 찾음 |
| `missing` | 임의 문자열 20개 | 0건 |

`LIKE` 열이 "못 찾음"인 유형은 변형한 문자열이 원래 이슈의 어느 필드에도 없는 경우만 남긴다. 단어를 임의로 반으로 나누는 규칙은 `업데 이트`처럼 실제로 입력하지 않을 검색어를 만들어 제외했다.

**추가 식별자 표본.** 기존 검색어 1,731개와 `missing` 20개는 그대로 두고, 전체 이슈에서 식별자가 있는 이슈를 유형별로 독립 추가 표집했다. 원문·코드 블록은 표집에 사용하지만 HTTP(S) URL은 제외한다. 각 유형에서 적격 이슈를 섞어 최대 300개를 뽑고, 이슈별 검색어 선택은 `(seed, issueId, type)` 난수를 쓴다. 기존 검색어 생성 난수에는 영향을 주지 않는다.

| 추가 유형 | 적격 이슈 | 표본 |
|---|---:|---:|
| camel 뒷부분 | 347 | 300 |
| camel 앞부분 | 338 | 300 |
| 점 경로 마지막 부분 | 1,138 | 300 |
| snake 일부 | 848 | 300 |
| kebab 일부 | 398 | 300 |
| 슬래시 경로 일부 | 140 | 140 |

유효 검색어는 3,371개이고 `missing`이 20개다. 집계의 `legacyAll`은 기존 표본, `identifierAll`은 추가 표본, `all`은 둘의 합이다.

**비교 대상.** 모두 같은 JVM과 같은 DB에서 실행한다.

- `like`: 현행 DB 검색. 검색어 전체를 `%검색어%`로 비교, 날짜순.
- `likeAnd`: 공백으로 나눈 단어마다 LIKE를 걸고 AND. DB 쪽을 최소한으로 고쳤을 때의 기준선. 날짜순.
- `lucene`: 관련도순. `luceneDate`: 같은 hit를 날짜순으로.

**지표.** 찾은 비율(전체 결과 안), 상위 5·10·20건 안 비율, MRR, 첫 페이지 응답 시간. 응답 시간은 실제 `IssueSearchService` 호출이며 HTTP·렌더링은 제외한다. 검색어마다 1회 예열 후 3회 중 중앙값을 쓰고, 그 값의 p50/p95를 낸다.

**환경.** 평가 데이터(이슈 4,882건, 댓글 6,335건)를 전용 MariaDB 10.11 컨테이너(`utf8mb4_unicode_ci`)에 복원한다. 빈 DB에서 새 JVM으로 실행했다. 관리자 권한, 단일 클라이언트, JDK 21.0.6, 최대 heap 1 GiB다. 전체 측정은 38분 만에 끝났다.

## Lucene 검색 구현

- 따옴표 밖 검색어는 공백으로 나누지 않고 한 문자열로 Nori 분석한다. 단어마다 따로 분석하면 앞뒤 문맥이 달라져 색인과 다르게 분해된다.

  | 텍스트 | 색인(문장 단위) | 검색어(단어 단위) |
  |---|---|---|
  | `교수님의` | `교수` | `교수` + `님의` |
  | `길이` (`길이 제한`) | `길` | `길이` |
  | `열수` (`열수 있도록`) | `수` | `열수` |

  토큰마다 제목·본문·댓글 중 하나에 있으면 되고 모든 토큰이 필요하다. 따옴표 구문 검색과 제목 가중치 3은 그대로다.
- 제목·본문·댓글마다 식별자 보조 필드를 하나 둔다. `WhitespaceTokenizer` → `WordDelimiterGraphFilter` → 소문자 변환으로 원형과 camelCase·PascalCase·snake_case·kebab-case·점·슬래시 경로의 부분을 색인한다. 약어 경계(`HTTPResponse`)와 한글이 붙은 경계도 분리한다. 색인할 때만 그래프를 평탄화하고 검색어 분석에서는 그래프를 유지한다.
- 한 검색어가 여러 부분으로 나뉘면 **같은 필드에서 순서대로 인접한 구문**으로 요구한다. `PointerException`이 떨어져 있는 `pointer … exception`까지 찾는 AND보다 오탐이 적다. 공백으로 구분된 검색어끼리는 모두 필요하다. 큰따옴표 안은 Nori 구문 검색만 쓴다. 댓글의 두 필드 모두 position gap 100을 둔다.
- **보조 경로 가중치는 0**이다. Nori에 이미 일치한 문서는 보조 경로에서 제외하고, 추가로 일치한 문서만 기존 결과 뒤에 붙인다. 작은 양수도 낮은 BM25 결과를 앞지를 수 있어 0으로 했다. 보조 결과끼리는 관련도를 구분하지 않고 Lucene 문서 순서를 따른다.
- 보조 필드만 일치한 결과는 스니펫과 댓글 링크를 생략한다. 보조 일치를 Nori 분석기로 잘못 강조하지 않기 위해서다.
- 색인 commit의 `yona.issue-search.version=3`이 없거나 다르면 내용 지문이 같아도 전체 재색인한다. 실패하면 이전 commit으로 롤백하고 부분 색인을 공개하지 않는다.

## 해석

- LIKE로 못 찾는 6개 유형에서 Lucene은 93–100%를 찾는다. 단어별 LIKE AND는 떨어진 단어·어순·식별자는 찾지만 활용형·조사·붙여 쓰기는 0–8%다.
- 단어별 LIKE AND는 단어 수만큼 본문·댓글 LIKE가 늘어나 p95가 79.50ms다.
- Lucene 관련도순은 p50 4.29ms로 LIKE보다 빠르다. 날짜순은 p50 58.20ms로 LIKE보다 느리다.
- **Lucene은 결과가 넓다.** 형태소 단위로 일치시키므로 결과 건수가 많다. 순위는 BM25만 쓰며 단어가 붙어 있는지는 반영하지 않는다. 코드 이름 부분 검색으로만 찾은 결과는 0점이라 Nori 결과 뒤에 붙고, 첫 페이지에 모두 들어오지는 않는다.
- LIKE만 찾는 검색어는 `exact` 13건이다. 검색어 끝이나 필드 시작처럼 문맥이 달라지는 위치에서 Nori가 다르게 분해한 경우다.

## 한계

- 한국어 분석 때문에 놓치는 검색어가 73건 남는다(exact 13, separated 10, reordered 19, inflected 4, particle 6, joined 21). Nori의 문맥·형태소 경계와 자동 변형 규칙의 한계다.
- 추가 식별자 표본의 100%는 임의 부분 문자열을 찾는 LIKE와 같다는 보장이 아니다.
- 검색어는 원문에서 자동으로 만든 것이며 실제 사용자 검색 로그가 아니다. 규칙이 만든 검색어가 어색한 경우가 남아 있다(예: `particle`의 일부).
- 정답이 원래 이슈 하나뿐이다. 다른 관련 이슈가 앞에 오는 것은 실패가 아니지만 순위 지표에서는 불리하게 잡힌다. 정밀도(엉뚱한 결과 비율)는 재지 않았다.
- 관리자 권한, 단일 클라이언트, MariaDB 하나에서만 쟀다. HTTP·렌더링·동시 부하는 측정하지 않았다.
- 검색 회귀 테스트 22개가 통과했다. 약어·한글 경계, 댓글·큰따옴표 경계, 이전 색인 재생성·실패 롤백, Nori 점수 보존, 배치 reader·큐·서비스 동작을 포함한다. 이 측정에서 전체 H2 회귀 테스트는 실행하지 않았다.

## 재현

[측정 드라이버](../src/test/kotlin/com/github/yonaprojects/yona/domain/issue/IssueSearchQualityProbe.kt)를 [Gradle init script](../support-script/search-poc/resource-probe.gradle)의 `searchQualityProbe`로 실행한다. 리소스 측정과 같이 빈 전용 DB와 존재하지 않는 출력 디렉터리가 필요하다.

```sh
export YONA_PROBE_ARCHIVE=/absolute/path/to/migration.zip
export YONA_PROBE_OUTPUT=/tmp/yona-search-quality-r1
export YONA_PROBE_JDBC=jdbc:mariadb://127.0.0.1:PORT/EMPTY_PROBE_DB
export YONA_PROBE_DB_PASSWORD=DISPOSABLE_DB_PASSWORD
# 선택: YONA_PROBE_SAMPLE=300 YONA_PROBE_SEED=843 YONA_PROBE_AS=<loginId>
# 선택: YONA_PROBE_CASES_OUTPUT=/private/path/cases.json  # 검색어 원문 포함. 저장소에 넣지 않는다.
./gradlew searchQualityProbe --init-script support-script/search-poc/resource-probe.gradle
```

측정 드라이버는 복원·색인·표집 단계를 출력하고, 검색 측정 중에는 약 30초마다 완료 건수·전체 건수·경과 시간을 출력한다. 출력은 개별 검색어 측정 사이에만 하므로 응답 시간 구간에는 포함되지 않는다. 한 검색어가 멈추면 진행 로그도 멈춘다. 실행은 background job으로 관리하고 외부 실행 제한 시간을 둔다.

전체 순위 평가를 위해 배치 결과를 모으되, 첫 페이지 시간은 제품의 `IssueSearchService.search`를 그대로 호출해 측정한다. 표집 규칙·seed·예열 1회·측정 3회 중앙값을 쓴다.

집계는 [search-quality-results.json](search-quality-results.json)에 보관하며 이 문서의 값은 `latest`다. 검색어 원문과 검색어별 결과는 저장소에 포함하지 않는다. 출력 경로는 Git worktree 밖이어야 한다.
