## 방법

**정답 이슈 찾기(known-item).** 이슈를 무작위로 300개 뽑고(seed 843), 각 이슈의 제목·본문·댓글 문장을 아래 규칙으로 바꿔 검색어를 만든다. 원래 이슈가 결과에 있는지, 몇 번째인지를 잰다. 사람이 관련도를 판정하지 않으며 원문을 공개하지 않고도 재현할 수 있다.

| 유형 | 규칙 | LIKE |
|---|---|---|
| `exact` | 연속된 한글 두 단어 그대로 (대조군) | 찾음 |
| `separated` | 같은 문장에서 3–7단어 떨어진 두 단어 | 못 찾음 |
| `reordered` | 연속된 두 단어의 순서를 바꿈 | 못 찾음 |
| `inflected` | `배포했습니다` → `배포된`, `복구됩니다` → `복구하는` | 못 찾음 |
| `particle` | 조사 교체 `오류가` → `오류를`. 어간이 같은 이슈에 다른 형태로도 있을 때만 | 못 찾음 |
| `joined` | 조사·어미 없는 두 단어를 붙임 `권한 설정` → `권한설정` | 못 찾음 |
| `identifierSplit` | `user_id`, `com.example.Foo`의 구분자를 공백으로 | 못 찾음 |
| `identifierPart` | `NullPointerException` → `PointerException` | 찾음 |
| `missing` | 임의 문자열 20개 | 0건 |

`LIKE` 열이 "못 찾음"인 유형은 변형한 문자열이 원래 이슈의 어느 필드에도 없는 경우만 남긴다. 단어를 임의로 반으로 나누는 규칙은 `업데 이트`처럼 실제로 입력하지 않을 검색어를 만들어 제외했다.

**비교 대상.** 모두 같은 JVM과 같은 DB에서 실행한다.

- `like`: 현행 DB 검색. 검색어 전체를 `%검색어%`로 비교, 날짜순.
- `likeAnd`: 공백으로 나눈 단어마다 LIKE를 걸고 AND. DB 쪽을 최소한으로 고쳤을 때의 기준선. 날짜순.
- `lucene`: 관련도순. `luceneDate`: 같은 hit를 날짜순으로.

**지표.** 찾은 비율(전체 결과 안), 상위 5·10·20건 안 비율, MRR, 결과 건수, 첫 페이지 응답 시간. 응답 시간은 실제 `IssueSearchService` 호출이며 HTTP·렌더링은 제외한다. 검색어마다 1회 예열 후 3회 중 중앙값을 쓰고, 그 값의 유형별 p50/p95를 낸다. 상위 5·10건 지표는 식별자 재측정부터 기록한다.

**환경.** 평가 데이터(이슈 4,882건, 댓글 6,335건)를 전용 MariaDB 10.11 컨테이너(`utf8mb4_unicode_ci`)에 복원. 관리자 권한. JDK 21, `-Xmx1g`. 수정 전·후 구현을 새 JVM·빈 DB에서 순서대로 실행했다.

## 수정한 결함: 검색어를 단어마다 따로 분석

첫 측정에서 LIKE가 찾는 `exact` 검색어 일부가 Lucene에서 0건이었다. `SimpleQueryParser`가 검색어를 공백으로 자른 뒤 단어마다 Nori로 분석하는데, Nori는 앞뒤 문맥에 따라 다르게 분해한다.

| 텍스트 | 색인(문장 단위) | 검색어(단어 단위) |
|---|---|---|
| `교수님의` | `교수` | `교수` + `님의` |
| `길이` (`길이 제한`) | `길` | `길이` |
| `열수` (`열수 있도록`) | `수` | `열수` |

[`2ee28a5`](https://github.com/Clickin/yona-spring/commit/2ee28a5a1510ff68d6a1fee7db606a04362b8053)에서 따옴표 밖 텍스트를 한 문자열로 분석하도록 바꿨다. 토큰마다 제목·본문·댓글 중 하나에 있으면 되고 모든 토큰이 필요하다. 따옴표 구문 검색과 제목 가중치 3은 그대로다. `lucene-queryparser`가 필요 없어져 Lucene JAR는 9개 14.95 MiB에서 6개 13.92 MiB(14,601,137 bytes)로 줄었다. H2 회귀 500개 통과(분석 회귀 테스트 1개 추가).

## 해석

- LIKE로 못 찾는 6개 유형에서 Lucene은 93–100%를 찾는다. 현행 LIKE는 0%, 단어별 LIKE AND는 떨어진 단어·어순·식별자는 찾지만 활용형·조사·붙여 쓰기는 0–8%다.
- 단어별 LIKE AND도 응답 시간 p95가 92ms로, 단어 수만큼 본문·댓글 LIKE가 늘어난다.
- **Lucene은 결과가 넓다.** 형태소 단위로 일치시키므로 결과 건수가 많고, 원래 이슈가 첫 페이지에 드는 비율은 대조군(`exact`)에서 LIKE 86.6%, Lucene 58.6%다. 순위는 BM25만 쓰며 단어가 붙어 있는지는 반영하지 않는다. 근접도 가산점이 다음 개선 대상이다.
- **당시 LIKE만 찾는 경우가 남았다.** `exact` 13건은 검색어 끝이나 필드 시작처럼 문맥이 달라지는 위치에서 Nori가 다르게 분해한 경우다. `identifierPart` 8건은 식별자 보조 필드가 없어서 놓쳤다. 아래 재측정에서 이 8건은 모두 찾았다.

## 한계

- 검색어는 원문에서 자동으로 만든 것이며 실제 사용자 검색 로그가 아니다. 규칙이 만든 검색어가 어색한 경우가 남아 있다(예: `particle`의 일부).
- 정답이 원래 이슈 하나뿐이다. 다른 관련 이슈가 앞에 오는 것은 실패가 아니지만 순위 지표에서는 불리하게 잡힌다. 정밀도(엉뚱한 결과 비율)는 재지 않았다.
- 관리자 권한, 단일 클라이언트, MariaDB 하나에서만 쟀다. 응답 시간은 같은 실행 안에서만 비교한다. 두 실행 사이의 차이는 실행 간 편차를 포함한다.

## 재현

[측정 드라이버](../src/test/kotlin/com/github/yonaprojects/yona/domain/issue/IssueSearchQualityProbe.kt)를 [Gradle init script](../support-script/search-poc/resource-probe.gradle)의 `searchQualityProbe`로 실행한다. 리소스 측정과 같이 빈 전용 DB와 존재하지 않는 출력 디렉터리가 필요하다.

```sh
export YONA_PROBE_ARCHIVE=/absolute/path/to/migration.zip
export YONA_PROBE_OUTPUT=/tmp/yona-search-quality-r1
export YONA_PROBE_JDBC=jdbc:mariadb://127.0.0.1:PORT/EMPTY_PROBE_DB
export YONA_PROBE_DB_PASSWORD=DISPOSABLE_DB_PASSWORD
# 선택: YONA_PROBE_SAMPLE=300 YONA_PROBE_SEED=843 YONA_PROBE_AS=<loginId>
# 선택: YONA_PROBE_CASES_OUTPUT=/private/path/cases.json  # 검색어 원문 포함. 저장소에 넣지 않는다.
./gradlew searchQualityProbe --init-script support-script/search-poc/resource-probe.gradle
```

측정 드라이버는 복원·색인·표집 단계를 출력하고, 검색 측정 중에는 약 30초마다 완료 건수·전체 건수·경과 시간을 출력한다. 출력은 개별 검색어 측정 사이에만 하므로 응답 시간 구간에는 포함되지 않는다. 한 검색어가 멈추면 진행 로그도 멈춘다. 실행은 background job으로 관리하고 외부 실행 제한 시간을 둔다.

현재 드라이버는 `814c069a9a134df9084bbe4bcc8901ee37d624e2`의 `withSearch`·`forEachBatch` API를 사용한다. 전체 순위 평가를 위해 배치 결과를 모으되, 첫 페이지 시간은 제품의 `IssueSearchService.search`를 그대로 호출해 측정한다. 표집 규칙·seed·예열 1회·측정 3회 중앙값은 변경하지 않았다. 이전 커밋을 재현하려면 당시 문서 브랜치의 드라이버를 사용한다.

집계는 [search-quality-results.json](search-quality-results.json)에 문맥 분석 수정 전·후(`before`, `after`)와 식별자 보조 필드 전·후(`identifierBefore`, `identifierAfter`)로 보관한다. 검색어 원문과 검색어별 결과는 저장소에 포함하지 않는다. 출력 경로는 Git worktree 밖이어야 한다.

## 식별자 보조 필드 재측정

### 설계

- 제목·본문·댓글마다 보조 필드 하나를 추가했다. 기존 의존성의 `WhitespaceTokenizer` → `WordDelimiterGraphFilter` → 소문자 변환으로 원형과 camelCase·PascalCase·snake_case·kebab-case·점·슬래시 경로의 부분을 색인한다. 색인할 때만 그래프를 평탄화하며 검색어 분석에서는 그래프를 유지한다.
- 한 검색어가 여러 부분으로 나뉘면 **같은 필드에서 순서대로 인접한 구문**으로 요구한다. `PointerException`이 떨어져 있는 `pointer … exception`까지 찾는 AND보다 오탐을 줄인다. 공백으로 구분된 검색어끼리는 기존처럼 모두 필요하다.
- Nori 경로는 따옴표 밖 전체 문자열을 한 번에 분석한다. 혼합 검색어도 이 분석의 offset을 사용하므로 한글을 단어마다 다시 분석하지 않는다. 큰따옴표 안은 기존 Nori 구문 검색만 사용한다. 댓글의 두 필드 모두 position gap 100을 유지한다.
- **보조 경로 가중치는 0**이다. Nori에 이미 일치한 문서는 보조 경로에서 제외하고, 추가 일치만 기존 결과 뒤에 붙인다. 작은 양수도 낮은 BM25 결과를 앞지를 수 있어 0으로 시작했다. 이번 측정에서 기존 적중 결과의 순위 하락이 없어 그대로 유지했다. 보조 결과끼리는 관련도를 구분하지 않고 Lucene 문서 순서를 따른다.
- 보조 필드만 일치한 결과는 스니펫과 댓글 링크를 생략한다. 기존 Nori 스니펫은 HTML 이스케이프와 최신 내용 지문 확인을 유지한다. 보조 일치를 기존 분석기로 잘못 강조하지 않는다.
- 색인 commit의 `yona.issue-search.version=2`가 없거나 다르면 내용 지문이 같아도 전체 재색인한다. 실패하면 이전 commit으로 롤백하고 부분 색인을 공개하지 않는다. 기본 `backend=db`와 DB 검색은 변경하지 않았다.

### 표본과 재현성

동일한 도구를 `2ee28a5`와 변경 구현에 각각 실행했다. sample 300, seed 843을 유지하고 매 실행 빈 MariaDB 10.11 DB를 썼다. 기존 1,731개 검색어와 `missing` 20개는 그대로 두고, 전체 이슈에서 식별자가 있는 이슈를 유형별로 독립 추가 표집했다. 원문·코드 블록은 표집에 사용하지만 HTTP(S) URL은 제외한다.

각 유형에서 적격 이슈를 독립적으로 섞어 최대 300개를 뽑고, 이슈별 검색어 선택은 `(seed, issueId, type)` 난수를 쓴다. 기존 검색어 생성 난수에는 영향을 주지 않는다.

### 응답 시간과 색인 크기

단위는 ms, 첫 페이지 20건의 p50 / p95다.

| 표본·검색 | 전 | 후 |
|---|---:|---:|
| 기존 표본 LIKE | 57.55 / 72.27 | 56.76 / 70.31 |
| 기존 표본 Lucene | 9.19 / 37.90 | 9.02 / 36.03 |
| 추가 식별자 Lucene | 13.16 / 42.05 | 13.86 / 43.13 |
| 전체 LIKE | 60.07 / 119.57 | 59.90 / 119.81 |
| 전체 단어별 LIKE AND | 82.71 / 160.94 | 81.91 / 159.18 |
| 전체 Lucene | 10.42 / 40.99 | 10.59 / 42.35 |

전체 Lucene p50은 1.6%, p95는 3.3% 늘었다. 이전 공개 실행의 5.16 / 21.93ms와 직접 비교하지 않는다. 이번 기준선부터 9.19 / 37.90ms였고, LIKE도 함께 느려져 실행 환경 편차가 있다.

색인 파일은 **2,945,772→8,375,012 bytes (2.81→7.99 MiB, +184.3%, 2.84배)**다. 이전 기록 2.82 MiB와 비교해도 약 2.83배다. 세 보조 필드에 원형과 분해 토큰을 함께 저장한 비용이다. heap·초기 색인 시간은 이번에 다시 재지 않았다.

### 남은 실패와 검증

- 추가 식별자 57건을 놓쳤다(뒷부분 41, 앞부분 16). 50건은 표집 규칙과 `WordDelimiterGraphFilter`의 약어 경계가 다르다. 일반 예로 `getHTTPResponse`는 `get` + `httpresponse`로 분해되어 `Response`나 `getHTTP`가 기대한 부분과 맞지 않는다.
- 나머지 7건은 식별자와 한글이 바로 붙은 경우다. 공백 기반 보조 분석에서 두 문자 영역이 같은 토큰 부분으로 남는다. 약어와 문자 영역 경계를 추가로 쪼개는 처리는 넣지 않았다.
- 기존 한국어 실패 73건(exact 13, separated 10, reordered 19, inflected 4, particle 6, joined 21)은 그대로다. Nori 문맥·형태소 경계와 자동 변형 규칙의 한계이며 이번 보조 필드는 이를 바꾸지 않는다.
- 보조 결과의 순위는 개선 여지가 있다. 기존 순위를 보존하려고 0점으로 뒤에 붙였으므로, recall이 올라도 첫 페이지에 모두 들어오지는 않는다. 이 실험은 정밀도를 측정하지 않는다.
- 지정 init script로 **H2 회귀 505개 통과**. 식별자 조각, 한글 혼합 검색, 구문·댓글 경계, 실제 Nori 불용어, 구버전 디스크 재색인·실패 롤백, 스니펫 생략을 포함한다. 최초 실행에서 `의`를 불용어로 잘못 가정한 테스트를 실제 제거되는 `그리고`로 고쳤다. 제품 검색 동작은 바꾸지 않았다.
- 측정용 컨테이너와 임시 복원본은 측정·분석 후 삭제했다. 평가 입력은 변경하지 않았다.
